Access & scope

What the agent can do in the buyer's systems, under which identity, and how that is enforced.

ACC-01What actions can your agent take in our systems, and how are those permissions enforced at the moment a tool is called?

Why buyers ask

The buyer stays responsible for everything that happens in its systems. An agent acting outside its intended authority is a named risk in agent frameworks, and instructions in a prompt are not an enforcement mechanism.

What a strong answer looks like

Names every tool the agent can call and the scope of each, shows that limits are enforced in code where the tool is invoked (not in the prompt), and offers test results plus a sample action record that shows the scope applied.

Evidence to attach

  • Per-agent inventory of tools and actions, with the systems and scopes each one can touch.
  • Enforcement in code at the tool-invocation layer (allowlists, parameter validation, scoped credentials), not only in the prompt.
  • Test results showing out-of-scope calls are blocked.
  • Per-action records that show which scope or permission applied.

Not enough on its own

  • The model is instructed not to do X.
  • A workflow diagram with no enforcement point.

Template answer

The agent can call N tools: list tool, target system and allowed operations, e.g. "issue_refund on Stripe, up to EUR 200 per refund". Each call passes through enforcement layer, e.g. a tool gateway that checks allowlist, parameter limits, scoped credential before execution; calls outside scope are blocked and logged. We test this in CI suite / quarterly test, last run date, results attached. Each action record stores the scope that applied (sample attached).

ACC-02For every write in our systems, which identity performed it? Which agent and version, under which credential and scope, on whose behalf?Hard to evidence today

Why buyers ask

Agents often act through shared service accounts or human-style browser logins, so the buyer's own logs cannot tell the agent from a staff member, and the vendor's logs cannot be matched to the buyer's.

What a strong answer looks like

Each agent deployment has its own non-human identity in the buyer's systems, and every action record carries agent ID and version, credential ID, scope and the user, case or ticket it acted for, so the buyer's logs and the vendor's records can be joined.

Evidence to attach

  • A distinct non-human identity per agent deployment, visible in the buyer's system logs.
  • Each action record carries agent ID and version, credential ID (never the secret), scope, and the initiating user, case or ticket.
  • Credentials isolated from the model and injected per call.

Not enough on its own

  • A shared integration user for all agent traffic.
  • Identity known only inside the vendor's database.

Template answer

Each deployment uses a dedicated identity, identity name / service principal, which appears in your system audit logs. Every action record contains agent ID, agent version, credential ID (never the secret), scope, and the initiating user / case / ticket ID. Credentials are held in vault / KMS and injected per call; the model never sees them. A sample record joined to your system log is attached.

ACC-03What stops prompt injection or a manipulated tool chain from causing the agent to take an action in our systems?

Why buyers ask

Agents read untrusted content (emails, documents, web pages, tool outputs). If that content can steer a tool call, an attacker can act inside the buyer's systems through the agent.

What a strong answer looks like

Treats retrieved content as untrusted, validates tool choice and parameters before execution independently of the model, has red-team results that include indirect injection, and can detect unusual actions after the fact.

Evidence to attach

  • Separation of instructions from untrusted data, plus input and output filtering.
  • Validation of tool selection and parameters before execution.
  • Red-team results that include indirect injection through retrieved content.
  • Detection of out-of-pattern actions in the action records.

Not enough on its own

  • We use a safe model.

Template answer

Untrusted content (emails, documents, web pages, tool outputs) is kept separate from instructions by method. Before any tool call, validator checks tool choice and parameters against policy; the model cannot bypass it. Our last red-team exercise on date, by internal team / third party, covered direct and indirect injection; a summary is attached. Unusual actions are flagged by rule / monitor.

Action records

What is recorded for each agent action, and whether one action can be produced end to end.

ACT-01For any single agent action, can you produce the complete record? What triggered it, which inputs and sources it used, the exact tool call and arguments, the system's response, and the downstream effect.Hard to evidence today

Why buyers ask

Reviewers and examiners pick one case and ask you to walk through it. If the record is spread across chat transcripts, APM traces and the vendor UI, the answer takes days and cannot be checked.

What a strong answer looks like

Can pick any action and produce, in minutes, one record with trigger, inputs and sources, exact tool call and arguments, the system's response, timestamps and trace ID, with sensitive fields redacted.

Evidence to attach

  • A per-action record with trigger, inputs, retrieved sources, tool name, arguments (redacted where needed), the system response, timestamps and a trace ID.
  • A sample export for one real (redacted) case, produced on request in minutes.

Not enough on its own

  • A chat transcript without the tool calls.
  • Infrastructure logs only.

Template answer

Every action produces one record containing: trigger (event / user request), inputs and retrieved sources, tool name and arguments (with fields redacted), the target system's response, timestamps and trace ID. We can export the full record for any action or case within time. A redacted example for one real case is attached.

ACT-02Which model and version handled a given action, including actions served by versions you have since retired?Hard to evidence today

Why buyers ask

Vendors route between several models and providers. When a past decision is challenged, the buyer must know which model produced it, even if that model is gone.

What a strong answer looks like

Stores the provider, model name and pinned version on every action record, and keeps an inventory of retired versions with the dates they were in use.

Evidence to attach

  • Model provider, model name and pinned version stored on every action record.
  • A model inventory that keeps retired versions with their active dates.

Not enough on its own

  • A current list of providers with no per-action version.

Template answer

Each action record stores model provider, model name and pinned version, e.g. example. We keep a model inventory including retired versions and their active dates (link / attachment), so any past action can be matched to the model that handled it.

ACT-03Show every model endpoint and external service the agent actually called for our traffic, not just the list in your inventory.Hard to evidence today

Why buyers ask

An inventory says what should be called. Destination records show what was called, which is what data-flow and data-residency reviews need.

What a strong answer looks like

Records each outbound call per action (provider, endpoint, region) and periodically compares actual destinations with the declared sub-processor list for that buyer.

Evidence to attach

  • Per-action record of each outbound call (provider, endpoint, region).
  • A periodic summary per buyer comparing actual destinations with the declared sub-processor list.

Not enough on its own

  • A static sub-processor page.

Template answer

Each action record lists the outbound calls made: provider, endpoint, region. Every month / quarter we compare actual destinations for your traffic with the declared sub-processor list and share the result. The latest comparison is attached.

ACT-04Which documents and records contributed to each answer or action?

Why buyers ask

Reviewers need to trace an output back to its sources, both to check correctness and to confirm the agent only used data it was entitled to see.

What a strong answer looks like

Stores the ID and version of each document or record the agent used, and retrieval respects the access controls of the source system.

Evidence to attach

  • Source IDs (document, record, version) stored on the action record.
  • Entitlement checks that carry the source system's access controls into retrieval.

Not enough on its own

  • Citations shown in the UI but not retained.

Template answer

For each answer or action we store the IDs and versions of the sources used (document IDs, record IDs). Retrieval runs under the requesting user's permissions / a scoped identity, so the agent only sees what that user / that scope is entitled to. An example record with sources is attached.

ACT-05What is the lineage of the data used in a decision? Where did each input come from, and how current was it?

Why buyers ask

Insurance and lending regulators ask for data lineage, and stale or wrong inputs are a common root cause of bad decisions.

What a strong answer looks like

Documents data flows per use case and stores, with each decision, where every input came from and when it was retrieved.

Evidence to attach

  • Documented data flows per use case.
  • Input source and retrieval timestamp stored with the decision.

Not enough on its own

  • A generic architecture diagram.

Template answer

For use case, inputs come from sources. A data-flow diagram is attached. With each decision we store the source and retrieval time of every input, so you can see how current the data was at the time.

ACT-06For an adverse decision, can you give the specific reasons and the data relied on? A proprietary model is not an acceptable reason to withhold them.

Why buyers ask

Consumer-facing lenders and insurers must give specific reasons for adverse outcomes, and regulators reject vendor secrecy as an excuse.

What a strong answer looks like

Stores reason codes and the specific inputs relied on for each decision, and can produce an explanation for a specific adverse outcome from that record.

Evidence to attach

  • Reason codes and the specific inputs relied on, stored per decision.
  • A sample adverse-decision explanation produced from the stored record.

Not enough on its own

  • Global feature importance for the model.

Template answer

For each decision we store reason codes (list or link) and the specific inputs relied on. An explanation for an individual adverse outcome is generated from that stored record, not reconstructed later. A redacted sample is attached.

ACT-07For customer-facing agents, can you show per interaction that the conduct rules for our use case were met, such as AI disclosure, contact-time windows and contact-frequency limits?Hard to evidence today

Why buyers ask

In collections, servicing and sales, a single non-compliant contact can be a violation. Buyers want per-interaction proof, not a policy that the platform enforces rules.

What a strong answer looks like

Records, per interaction, the disclosure given, the local time of contact, the contact count at that moment and the rule version applied, so compliance can be shown for any single contact.

Evidence to attach

  • Per-interaction record of the disclosure given, the time in the customer's time zone, and the frequency counter at the time of contact.
  • Rule configuration and version applied to each interaction.

Not enough on its own

  • QA reviews a sample of calls.

Template answer

For each interaction we record the AI disclosure given (wording), the time in the customer's time zone, the contact-frequency count at that moment, and the version of the rule set applied (rule set). An export for a sample of N interactions is attached.

The specific conduct rules (for example debt-collection contact limits) come from the sector law for your use case and are not mapped here.

Outcome verification

Whether what the agent reports matches what actually happened in the system of record.

OUT-01When the agent says it did something, how do you know it actually happened in our system, as described?Hard to evidence today

Why buyers ask

An agent's own summary ("refund issued") is not evidence. Agents can report success while the target system shows an error, a different amount or nothing at all. Reviewers want the system of record's response next to the claim.

What a strong answer looks like

Stores the agent's claim next to the target system's actual response, optionally reads the object back from the system of record to confirm, and reports the mismatch rate to the buyer.

Evidence to attach

  • Each action record stores both the agent's claim and the target system's actual response (status, object ID, returned values).
  • Optional read-back that queries the system of record and records match or mismatch.
  • Mismatch rate per period, reported to the buyer.

Not enough on its own

  • The agent's final message.
  • HTTP 200 without checking the returned object.

Template answer

Each action record stores both what the agent reported and the response from target system (status, object ID, returned values). For high-impact actions, e.g. refunds we also read the object back from system and record match or mismatch. The mismatch rate for period was x (report attached).

OUT-02How do you detect and report actions that failed, only partly completed, or produced a different result than intended?Hard to evidence today

Why buyers ask

Silent failures are the hardest to catch. A buyer wants to see failures counted and reported, not discovered by a customer.

What a strong answer looks like

Counts failed, partial and mismatched actions per period with examples, has alert thresholds and owners, and reconciles high-impact actions against the system of record.

Evidence to attach

  • Failed, partial and mismatched actions counted per period, with examples, in the buyer's report.
  • Alert thresholds and owners.
  • Reconciliation against the system of record for high-impact actions.

Not enough on its own

  • Error rate from APM only.

Template answer

Failed, partial and mismatched actions are counted and included in your monthly report with examples. Alerts fire at threshold and go to owner. For action types we reconcile against system every period. The last report is attached.

Tamper evidence

Whether records can be changed after the fact without anyone noticing, and who can check.

TMP-01Are agent action records protected so that any edit, deletion, reordering or truncation after the fact is detectable?Hard to evidence today

Why buyers ask

Access controls protect logs from outsiders, not from the party that writes them. "Immutable" is a claim; reviewers increasingly ask for the mechanism.

What a strong answer looks like

Names the mechanism: hash-chained, signed records with keys separated from operators, and periodic commitments (for example Merkle roots) so edits, deletions, reordering and truncation are all detectable.

Evidence to attach

  • Hash-chained, append-only records (each record commits to the previous one).
  • Digital signatures with keys separated from application operators.
  • Periodic commitment of segment digests (for example a Merkle root) so truncation is detectable.
  • Synchronized clocks and documented key management.

Not enough on its own

  • "Logs are immutable" with no mechanism.
  • Write-protected storage alone, where the vendor still controls the storage.

Template answer

Action records are append-only and hash-chained: each record includes the hash of the previous one. Records are signed with Ed25519 / P-256 keys held in KMS / HSM, separate from the people who run the agent. Every period we commit a digest of the latest segment to an external log / to you, so truncation is also detectable. Key management is documented in document.

TMP-02Can we, our auditor or our regulator verify those records ourselves, without access to your systems and without relying on your word?Hard to evidence today

Why buyers ask

Logs the vendor writes, stores and attests to are self-reported evidence. The strongest records are those a third party can check independently.

What a strong answer looks like

Gives the buyer an exported bundle and a verification tool they run themselves, offline, with documented public keys and digests anchored outside the vendor, plus a demo of a tampered bundle failing.

Evidence to attach

  • A verification tool the buyer can run offline on an exported bundle.
  • Public keys and verification steps documented.
  • Record digests anchored outside the vendor (for example an append-only transparency log) or held by the buyer.
  • A worked example showing a tampered bundle failing verification.

Not enough on its own

  • A screenshot or PDF export from the vendor's UI.
  • A SOC 2 report, which covers controls, not individual records.

Template answer

You can verify records yourself. We export a bundle for any period; you run verifier, e.g. an open-source CLI offline against it with our published public key key ID. Segment digests are also anchored in external log / your storage, so we cannot rewrite history without detection. A sample bundle, the verification steps and a tampered example that fails are attached.

FINOS, AIUC-1 (E015.4, supplemental) and CSA AARM (R5, offline-verifiable signatures) state independent verifiability explicitly. Elsewhere it follows from audit and access rights.

TMP-03Who at your company can read, change or delete agent records, and is that access itself logged?

Why buyers ask

Privileged insiders are the main threat to record integrity. Reviewers expect named roles and an access trail.

What a strong answer looks like

Lists the named roles with access to record storage and signing keys, logs each access against an individual identity, and separates people who run the agent from people who can touch records or keys.

Evidence to attach

  • Named roles with access to record storage and keys.
  • Access to records logged against individual identities and reviewed.
  • Separation between people who run the agent and people who can touch records or keys.

Not enough on its own

  • "Only engineers have access."

Template answer

Access to record storage is limited to roles, number of people; access to signing keys to roles. Every access is logged against an individual identity and reviewed frequency. People who operate the agent cannot change records or keys. The latest access review is attached.

Why buyers ask

Insurers and banks are expected to secure audit rights over third-party AI. A SOC 2 report usually covers infrastructure and access, not agent behaviour.

What a strong answer looks like

Grants audit rights that cover the AI system itself and provides reports whose scope includes agent behaviour, together with record samples the buyer can verify.

Evidence to attach

  • Audit-rights clause covering the AI system.
  • Reports whose scope includes agent behaviour, plus record samples the buyer can verify.

Not enough on its own

  • A SOC 2 report alone.

Template answer

Contract clause gives you audit rights over the AI system, including model use, agent actions, records. Our SOC 2 Type II / other report covers scope. For agent behaviour we provide verifiable record samples for any period you choose.

SUB-03Will you cooperate with regulatory inquiries and give examiners access to the documentation and records they ask for?

Why buyers ask

Regulators examine the buyer, and through the buyer, its AI vendors. Buyers need the cooperation in writing and the artifacts ready.

What a strong answer looks like

Commits in writing to cooperate with regulators and keeps an evidence package ready: model documentation, validation, change history and verifiable action records.

Evidence to attach

  • Regulatory cooperation clause.
  • A ready evidence package: model documentation, validation, change history and verifiable action records.

Not enough on its own

  • Best-effort cooperation with no artifacts.

Template answer

Contract clause commits us to cooperate with your regulators and to give examiners access to documentation and records. We keep an evidence package ready: model documentation, validation results, change history and verifiable action records, deliverable within time.

Framework references (5)
  • NAIC AI Bulletin Sec. 3, 4.2(b); Sec. 4: Cooperation with regulatory inquiries; documents regulators may request (verified)
  • NYDFS CL7 ¶9; ¶37: DFS exam authority; cooperation clause (verified)
  • DORA Art. 30(2)(g): Full cooperation with competent authorities (verified)
  • EU AI Act Art. 18: Provider documentation kept for authorities (verified)
  • ISO 42001 A.8.5: Information for interested parties incl. regulators (secondary source)
